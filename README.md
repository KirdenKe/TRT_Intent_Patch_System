# Evidence-Gated TRT Intent and Digital Twin System

This repository implements a human-reviewed workflow for converting natural-language production-line requests into versioned Task Requirement Table (TRT) changes, generating multiple candidate strategies, evaluating every compilable candidate in Isaac Sim, and presenting the best eligible strategy to the operator with traceable evidence.

The system combines:

- n8n chat orchestration and session state;
- a FastAPI service (`trt-api`) for deterministic validation, persistence, strategy generation, simulation orchestration, evidence extraction, and ranking;
- one configured production vLLM for intent interpretation and exploratory strategy generation;
- an external Windows Isaac Sim host runner;
- file-backed, versioned artifacts for audit and reproducibility;
- Milestone 12 data collection and comparison-test tooling with provenance gates.

No real production equipment is controlled by this repository. The deployment endpoint performs a simulated/local state transition only. Automated Milestone 12 comparison mode suppresses even that simulated deployment.

## Current Workflow

The operator-facing path is:

1. The operator enters a natural-language request through the active n8n chat workflow.
2. The dialogue layer classifies the turn as a task change, configuration query, help, approval, deployment decision, cancellation, or unsupported/unclear input.
3. For a task change, the Intent Generator creates a structured candidate patch. Python validation checks required fields, schema, allowed values, line scope, numeric values, and protected fields.
4. The operator reviews and approves the IntentPatch. Approval creates a versioned TRT release and audit records.
5. The Supervisor aligns the released TRT with current state records and produces a reconciliation plan.
6. `trt-api` creates a candidate-strategy batch containing one deterministic operator-faithful baseline and additional exploratory candidates from the configured production LLM.
7. Each candidate that passes deterministic validation is compiled into its own ScenarioSpec and run through Isaac Sim sequentially. A process-wide lock prevents concurrent Isaac runs.
8. RunArtifacts and evidence are evaluated against mandatory safety and correctness gates.
9. Eligible strategies are ranked by mean per-line throughput attainment. Ties prefer lower in-simulation strategy duration and then candidate ID.
10. n8n shows the selected strategy, alternatives, evidence, warnings, and rejection reasons to the operator.
11. The operator may accept the selected result, decline it, or revise the request. Only simulated deployment is implemented.

The operator approves the IntentPatch once; the system evaluates the resulting strategy batch. The current UI does not let the operator deploy an arbitrary lower-ranked candidate directly.

## Candidate Evaluation

Candidate batches contain 2-8 strategies, with a default of 3:

- Candidate 1 is a deterministic, operator-faithful baseline. It applies the requested changes without exploratory reinterpretation.
- Remaining candidates are generated by the same configured production LLM using exploratory prompt roles. TC7 model-comparison tests are separate and do not mix models inside a normal production batch.
- Invalid model output may be regenerated before simulation using deterministic validation feedback.
- Simulation failure does not trigger post-simulation LLM regeneration. If all candidates have conclusive but ineligible evidence, the operator is asked to refine the request. If evidence is incomplete because of a system, simulator, ScenarioSpec, RunArtifact, or evidence-pipeline problem, the system reports a recovery issue instead of blaming the operator input.

The mandatory eligibility gates are:

- a completed RunArtifact and readable evidence;
- evidence that does not prohibit deployment;
- complete placement records with `R_storage = 1`;
- zero manipulator-priority deviations;
- zero batch-gating violations;
- throughput evidence for every simulated line;
- actual throughput for every simulated line greater than or equal to that line's target throughput.

`R_reset` is retained as a diagnostic thesis metric. Missing reset evidence produces a data-quality warning but is not a candidate-selection constraint.

The ranking objective is:

```text
throughput_attainment = mean(actual_throughput_per_hour / target_throughput_per_hour)
                         across all simulated lines
```

Ranking occurs only after all mandatory gates pass. Isaac Sim calculates candidate evidence; `trt-api` performs eligibility checks and comparison.

## Capability Boundary

The system currently performs:

- natural-language intent classification and structured field extraction;
- clarification for missing or ambiguous fields;
- deterministic schema, range, semantic, and protected-field validation;
- versioned TRT release and state reconciliation;
- multiple candidate-strategy generation;
- ScenarioSpec generation;
- sequential digital-twin feasibility and KPI evaluation;
- evidence-based candidate filtering and ranking;
- explicit rejection and recovery reasons;
- operator review before simulated deployment;
- provenance-aware test and report data collection.

The system does not currently provide:

- general job-shop scheduling or combinatorial production optimization;
- proof that the selected strategy is globally optimal;
- automatic transfer to PLCs, robots, or other physical production equipment;
- a complete Real-to-Sim or Sim-to-Real pipeline;
- production safety certification.

## Prerequisites

- Windows host for the supplied Isaac Sim runner scripts.
- Docker Desktop with Docker Compose.
- Python 3.11 or newer for host-side tools and tests.
- A working Isaac Sim installation and the external `pick_up_example.py` project.
- Network access to the configured vLLM endpoint.
- n8n workflow data or permission to import and publish the supplied workflows.

Install the host Python package:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"
```

Copy the environment template before starting Docker services:

```powershell
Copy-Item .env.example .env
```

Review these two configuration surfaces:

| Concern | Configuration location | Notes |
| --- | --- | --- |
| Production vLLM used by `trt-api` | `.env` | Set `VLLM_CHAT_COMPLETIONS_URL` and `VLLM_MODEL`. |

## Start The System

### 1. Start the Isaac host runner

First edit `data/isaac_host_config.json` for the local Isaac installation, script path, working directory, and Docker/host artifact mapping. Then run:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\start_host_isaac_runner.ps1
```

The launcher validates all required paths and binds to `0.0.0.0` so Docker can
reach it. This command starts the HTTP bridge; Isaac Sim itself starts only
after `trt-api` submits an accepted run request. Keep the runner terminal open.

Verify it in another terminal:

```powershell
Invoke-RestMethod http://127.0.0.1:8765/health
```

See [docs/start_host_isaac_runner.md](docs/start_host_isaac_runner.md) for the authoritative host-runner setup, path mapping, troubleshooting, and handover notes.

### 2. Start Docker services

Validate the resolved configuration, then build and start the services:

```powershell
docker compose config
docker compose up -d --build
```

Verify the API and host-runner connection:

```powershell
Invoke-RestMethod http://localhost:8000/health
Invoke-RestMethod http://localhost:8000/debug/runtime-config
Invoke-RestMethod http://localhost:8000/debug/isaac-host-runner-status
```

Service URLs:

- `trt-api`: `http://localhost:8000`
- OpenAPI UI: `http://localhost:8000/docs`
- n8n: `http://localhost:5678`
- host runner on Windows: `http://127.0.0.1:8765`

### 3. Import and publish n8n workflows

On a fresh n8n installation, import the child workflows before the parent workflow:

```text
1. intent_to_patch_review.workflow.json
2. patch_release_approval.workflow.json
3. released_trt_to_reconciliation.workflow.json
4. generate_scenario_spec.workflow.json
5. chat_operator_task_allocation.workflow.json
```

The parent workflow ID is `ChatOperatorTaskAllocationDemo`. Its active child workflow IDs are:

- `IntentToPatchReviewDemo`
- `PatchReleaseApprovalDemo`
- `ReleasedTRTToReconciliationDemo`
- `GenerateScenarioSpecDemo`

Workflow files are mounted in the n8n container at `/home/node/.n8n/imports`. Example:

```powershell
docker compose exec n8n n8n import:workflow --input=/home/node/.n8n/imports/intent_to_patch_review.workflow.json
```

Import the remaining files in the order above, open n8n, verify that the Execute Workflow nodes resolve to the intended children, and publish the workflows. The public chat URL is created by the active Chat Trigger; do not assume an old webhook UUID remains valid after re-import.

Inside Docker, n8n calls FastAPI at `http://trt-api:8000`. It must not start FastAPI or Isaac Sim through an Execute Command node.

## n8n Workflow Roles

| Workflow file | Responsibility |
| --- | --- |
| `chat_operator_task_allocation.workflow.json` | Operator chat, session loading, early cancel/help/query routing, approval and deployment decisions, user-facing responses. |
| `intent_to_patch_review.workflow.json` | LLM-assisted domain extraction, deterministic normalization, validation, and candidate-patch review. |
| `patch_release_approval.workflow.json` | Operator release decision, TRT versioning, and audit persistence. |
| `released_trt_to_reconciliation.workflow.json` | Current-state loading and Supervisor reconciliation. |
| `generate_scenario_spec.workflow.json` | Candidate-batch generation, sequential ScenarioSpec/Isaac execution, evidence comparison, and selected-strategy response. |

Session context preserves identifiers such as `session_id`, `patch_id`, `release_id`, `audit_id`, `trt_id`, `trt_version`, `reconciliation_plan_id`, `strategy_batch_id`, `scenario_spec_ids`, and simulation run IDs. Child workflows must preserve existing non-null identifiers.

## Milestone 12

Milestone 12 distinguishes seed/gold fixtures, expanded fixtures, historical artifacts, live n8n executions, live API executions, and live Isaac runs. Fixture data is never measured performance.

Useful preparation and access checks:

```powershell
python -m tools.m12_verify_n8n_access
python -m tools.m12_seed_comparison_data --output outputs/reports/m12/seed_data
python -m tests.m12.run_comparison_tests `
  --seed-data outputs/reports/m12/seed_data `
  --output outputs/reports/m12/comparison_results `
  --dry-plan-only
```

Generate final figures only when the metrics database contains eligible live rows:

```powershell
python -m tools.m12_generate_figures `
  --input outputs/reports/m12/m12_metrics.sqlite3 `
  --require-live-data
```

The figure generator must reject missing provenance, zero-row inputs, and fixture-only performance data unless fixture preview mode is explicitly requested. Historical plots must be explicitly enabled and labeled historical.

Do not run the full comparison suite until the host runner, n8n workflow links, model endpoint, output mappings, and smoke queue have been checked.
